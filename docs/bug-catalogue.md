# Bug catalogue: the sightings behind the XDR/CAP-coverage RFP

Compiled 2026-11-17 from the RFP's "Supporting Signals" list
(https://stellar.gitbook.io/scf-handbook/scf-awards/build-award/rfp-track#current-open-rfps) and the GitHub API.
Every row was read at its source; nothing here is from memory.

Notes on the list itself:

- The RFP lists **18** public sightings. Two of them are not bugs: stellar-core#5435 is the `--check-lcm` feature the corpus must agree with, and stellar-etl#470 is a protocol-upgrade epic.
- The RFP's evaluation criteria refer to "one sighting from section 7"; the list is in section 6.
- Sighting dates in the RFP are close/merge dates or nearby, not always the date the item was opened.
- Reviewer checks name six of them: wallet-backend #729, #731, #716 (replay harness) and js-stellar-sdk #1766, #1785, #1789 (conformance runner).

## Root-cause classes

Used in the table and as the `coverage.rootCauses` vocabulary of the manifest schema.

| Class | Meaning |
| --- | --- |
| `unvalidated-passthrough` | The reader trusts a field stellar-core passes through without validating it (memo bytes, auth trees, muxed IDs, string contents). |
| `participants-from-envelope` | Participants or effects are derived from what the envelope claims, not from what the meta says changed. |
| `address-width` | An address or key form wider than the reader's storage or type (muxed `M…`, signed-payload `P…`, non-account `ScAddress` kinds). |
| `meta-only-change` | A ledger-entry change with no operation or event of the type the reader keys on, so it is silently dropped. |
| `canonical-order` | The reader orders values differently from core or the Soroban host (strkey text vs key bytes, map keys). |
| `lossy-conversion` | Conversion to a native type loses information (map keys collide, non-UTF-8 bytes replaced, float64 amounts). |
| `integer-domain` | A 64-bit or other integer is accepted or produced outside its domain, or in a non-canonical text form. |
| `unbounded-resource` | No cap on depth, length or allocation while decoding attacker-controlled structure. |
| `unknown-arm` | A union arm, enum value or type the reader's XDR does not know (old SDK pin, feature-gated XDR, new protocol). |
| `encode-decode-asymmetry` | Decode then encode does not reproduce the bytes, or two code paths render the same value differently. |

## What this demands from the manifest

1. **Three entry kinds.** 10 of the 16 real defects need a full `LedgerCloseMeta` (indexer bugs live in the meta); the SDK defects need a single small value; three (#16 partly, #17, #12's over-max half) are not XDR at all and need named SDK operation checks with inputs and expected outputs or errors.
2. **Expected values must reach into meta.** Rows 2, 3, 8, 9, 10 are all "the envelope says X, the meta says Y". The manifest needs expected ledger-entry changes and an expected participant set, both derived from meta.
3. **Pre-fix / post-fix references per sighting**, as commits (wallet-backend has no release tags) or tags (js-stellar-sdk), with the verdict expected on each side.
4. **Root cause and shape tags** so one entry can serve several sightings (row 3's ledger also covers producer 3 of row 8; row 2's covers part of row 9).
5. **Resource expectations** (rows 5, 12, and the "unbounded authorization trees" in the RFP text): depth and element counts recorded per entry so the harness can assert bounded memory.
6. **Provenance that distinguishes** network capture, local-core output (including stellar-core's own `--check-lcm` goldens, row 1) and synthetic values, with a statement of whether core could emit a synthetic value.
